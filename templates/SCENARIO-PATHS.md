# SCENARIO-PATHS · 场景操作路径（模板）

> 本项目实例：`docs/SCENARIO-PATHS.md`。本文件是脚手架模板，供后续病种复用。
> **在调研设计阶段的位置**：`docs/SCENARIOS.md`（场景是什么）之后、`docs/UI-DESIGN.md`（界面长什么样）之前。
> `SCENARIOS.md` 回答「患者要完成什么事」，本文件回答「**从首页出发，怎么一步步把这件事做完，再回到首页**」。
> 两者缺一不可：只写场景会做出「有页面但走不通」的产品；只写界面会做出「好看但不对应真实任务」的原型。

---

## 0 为什么要有这条增强

调研设计阶段已有的产物是「场景表」（触发 → 想完成的事 → 产物）。它有一个盲区：

> **场景是散的，首页是整的。** 每个场景单独看都成立，但没人验证过「一个真实的人从打开工作台开始，能不能走完它」。

结果常见的两类返工：
1. **有页面没路径** —— 功能都做了，但患者找不到入口，或走到一半不知道下一步点哪。
2. **有路径没回流** —— 做完了，回到首页发现什么都没变，患者不确定「刚才那下到底记上没」。

本文件用两个强制项堵住这两类返工：
- **每条场景必须写出「首页入口」和「返回首页看到什么变化」**，中间步骤不许跳。
- **增删改查必须明确默认走哪条路**——见 §2，患者不懂数据库，CRUD 不能直接摊给患者。

---

## 1 通用路径骨架（五步闭环）

所有场景共用同一条骨架。写路径时逐步对照，不许出现「然后用户就填好了」这种跳步。

| 步 | 名称 | 要回答的问题 | 反例（不合格） |
| --- | --- | --- | --- |
| 1 | **首页入口** | 患者从首页哪个元素进入？没选分野时这个入口在不在？ | 「从膀胱灌注页进入」——首页上没有指向它的东西 |
| 2 | **进入即知所处** | 进来第一眼看到什么，知不知道自己现在处在哪一步？ | 一进来是一个空白表单 |
| 3 | **完成动作** | 具体做什么（查 / 增 / 改 / 确认 / 导出），走 §2 的哪条路径 | 「录入信息」——录什么、怎么录 |
| 4 | **得到产物** | 手里多了什么可带走的东西（记录 / 清单 / 摘要 / 文件） | 「保存成功」——保存了什么，患者看得见吗 |
| 5 | **返回首页** | 回到首页，**哪个位置的什么内容变了**？没变的话，患者凭什么知道刚才生效了？ | 「返回首页」——然后就没了 |

> **第 5 步是本文件的立身之本**。首页是患者唯一会反复回到的地方；回流无变化 = 患者无法确认操作生效 = 会重复录入或放弃使用。

## 2 CRUD 交互模型：默认 AI 协助，手工是进阶

### 2.1 为什么不能把 CRUD 直接给患者

患者不是数据录入员。工作台一旦把「新增 / 编辑 / 删除」做成主界面上的一排按钮，会产生三个后果：

1. **门槛**：患者得先理解「这条记录属于哪个实体、有哪些字段」才能填，而绝大多数人不懂数据库结构，也不该懂。
2. **焦虑**：编辑入口多 = 随时可能改错 = 不敢点。而医疗数据「改错了」的心理成本远高于普通应用。
3. **责任错位**：让患者手工填医学字段，等于把「结构化」的活推给最没有结构化能力的一方。

**因此本项目的规定是：**

> **默认路径是 AI 协助** —— 患者只说一句自然语言（或贴一段原文、拍一张报告），系统产出**草稿**，患者做的是**逐项核对**，不是填表。
> **手工编辑是进阶路径**，默认折叠，且只出现在「确实需要精确录入」的少数位置。

### 2.2 六个动作的语义与约束

「增删改查」在实际使用中其实是六件事，必须分开设计——尤其**删**和**改**在医疗数据里不是普通 CRUD。

| 动作 | 患者的话 | 默认路径 | 硬约束（不可让步） |
| --- | --- | --- | --- |
| **查** | 「我灌注做到第几次了」 | 首页直接看得见；追问走 AI 协助 | 查不该需要任何操作——重要状态必须常显在首页 |
| **增** | 「下周三灌注第四次」 | **AI 协助**：说话 → 草稿 → 逐项核对 → 入库 | 草稿区与档案区**视觉必须分开**，草稿永远标「未经核对」 |
| **改** | 「日期记错了，是 10-30 不是 10-23」 | AI 协助（说一句改哪条）→ 确认 | **留痕不覆盖**：旧值保留，改动进变更记录；不可逆事实（如术式）必须走「新增修正记录 + 指向旧记录」 |
| **删** | 「这条记重了」 | AI 协助 → 确认 | **标失效，不物理删**。删除后仍可在变更记录里追溯；已生成的导出与摘要同步失效 |
| **确认** | 「这几条是对的」 | 逐项勾选（这是患者唯一必须亲手的动作） | 「已确认」只表示**转录核对**，不等于医学审核；界面必须写明这句 |
| **撤销** | 「刚才点错了」 | 一步撤销，不需解释 | 撤销本身也留痕 |

### 2.3 默认路径（AI 协助）的标准四步

```
① 说 / 贴 / 拍       患者用自然语言描述，或贴报告原文
        ↓
② 系统出草稿          结构化候选，逐条标「来自哪里」+「未核对」
        ↓
③ 逐项核对           患者只做三个选择：接受 / 改一下 / 不是这条
        ↓
④ 入库               确认后才进事实层；未确认的留在草稿区
```

**设计要点**：
- 第 ② 步**只抄写、不判断**——原文照录，认不出的字段留空，绝不猜。
- 第 ③ 步是**患者唯一的必修动作**，必须设计得极轻：一条一个卡片，一屏能看完，键盘可操作。
- 草稿区要有数量提示（「2 条待核对」），并出现在**首页**上——否则患者会忘了自己还有没核对的。

### 2.4 手工路径（进阶）什么时候出现

只在这三种情况下把手工编辑露出来，其余一律折叠：

| 场景类型 | 为什么要手工 | 设计口径 |
| --- | --- | --- |
| **批量重复录入** | 一次录一批比说一句话更快（例：一次录 3 天的造口更换） | 表格行内编辑，一次提交一批；型号从**可复用目录**里选，不重打 |
| **精确数值/日期** | 自然语言里的数字容易歧义 | 表单预填 AI 解析结果，患者只做修正 |
| **私密内容** | 患者可能不愿意对 AI 说 | 直接给输入框，本地存储，不进任何外发路径 |

> **判断标准**：如果一件事患者一个月只做一次、且字段少于 5 个，**不要给手工表单** —— 用 AI 协助。手工表单只在「重复」「精确」「私密」三种情况下才值得占用界面。

## 3 逐场景操作路径

每条场景按 §1 的五步写。**步骤里不许出现功能名或字段名**——写患者看得见、点得到的东西。

### S__ ＜场景名＞

| 项 | 内容 |
| --- | --- |
| **首页入口** | 从首页哪个元素进入；未选分野时该入口是否存在 |
| **进入即知所处** | 进来第一眼看到什么，怎么知道自己在哪一步 |
| **完成动作** | 走 §2 的哪条路径（查 / 增 / 改 / 确认 / 导出）；具体做什么 |
| **得到产物** | 手里多了什么可带走的东西 |
| **返回首页** | **哪个位置的什么内容变了** |
| **CRUD 归类** | 本场景主要涉及哪几个动作 |
| **依赖** | 依赖哪些场景/模块先完成；缺来源时如何降级 |

（按 `docs/SCENARIOS.md` 的场景总数逐条补全，编号必须一一对应，不许漏、不许新增。）

**通过标准**：
- 每条 P1 场景都有回流变化，且**不是**「弹了一个提示框」——提示框会消失，回流必须是页面上留下的状态。
- 首页任何一个位置承接的 P1 场景回流**不超过 4 条**，否则拆卡。
- 未选分野时，首页至少仍有 2 条可用路径（急症入口 + 先做的那件事）。

## 5 与验收锚点的衔接

本文件的路径是 `docs/ACCEPTANCE.md` 的输入。每条路径的第 5 步（回流）应转成一条可断言验收：

> 「完成 S__ 后返回首页，断言 ＜位置＞ 显示 ＜预期内容＞。

**未实际在原型里点过一遍的路径，不得标为已确认。**
